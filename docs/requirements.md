# LanNote 需求文档 v0.1

> 2026 年 11 月 3 日，晚上。
> 第一版，写给自己看，也写给以后可能加入的人看。不是承诺，随时会改。

---

## 0. 一句话

同一个局域网里，几个人能同时往同一张便签上写字——各写各的段落，各点各的确认，谁也不覆盖谁。

---

## 1. 为什么想做这个

我用过的便签软件不算少了。

Windows 自带便签只能自己看。Notion、飞书、语雀都能协作，但"协作"的前提是先注册、再联网、再建一个工作区、再把对方拉进来。为了在宿舍里传一句话，我要先说服室友装一个 App、注册一个账号、扫一个码。等这些做完，那句话我已经当面说完了。

真正想要的东西特别小：**几个人物理上就在同一个 WiFi 里，想一起写点东西。**

不需要云端，不需要账号，不需要把数据交给谁。数据就在我们之间这几台机器上。

另外说句实话：这是我要自己从头写完的第一个桌面软件。所以下面所有技术选择都会偏向"我一个人能做完、能讲清楚"，而不是"工业界的标准答案"。这个前提会影响后面很多决定，先摆在这儿。

---

## 2. 给谁用

眼下的目标用户只有一种：

> 一个宿舍、一间实验室、一个自习室里的 2~4 个人，连着同一个路由器，想一起记点东西。

**不打算服务**：跨网段的协作、陌生人协作、企业权限管理、几百人同时在线的大房间。

这个范围窄得有点丢人，但窄才能做完。

---

## 3. 核心场景

这是我心里那个画面，所有设计都为它服务：

下午三点，宿舍。

我在台式机上打开 LanNote，新建一张便签，标题写「下周实验安排」。
隔壁的人在笔记本上看到局域网里有张便签正在被编辑，点进去，加入。

我写第一段：

> 周一上午去借旋光仪，记得带上学生卡。

他写第二段：

> 周二下午三点 HPLC 换柱子，柱子在上次那个柜子里。

我写完了，点右上角的对勾——我这段定稿，落成便签的第一段。
他过一分钟也点对勾——他那段落在我后面，成了第二段。

全程没有加好友、没有注册、没有连外网，甚至不用说话。

---

## 4. 几个关键设计

这一节是整个文档最要紧的部分。技术可以换，这几条约定是项目的骨架。

### 4.1 便签是一串段落，不是一块画布

**这是最重要的一条。**

大多数协作文档把正文当成一整块富文本。两个人同时改同一块，就得做字符级合并（OT 或者 CRDT），复杂得可怕，而且这正是"我打的字被人吞了"这类事故的来源。

LanNote 换一个思路：

> **一次提交 = 一个段落。段落之间有明确边界，所以天然不冲突。**

只要两个人不往同一个段里挤，就永远不需要合并算法。冲突这个问题在数据模型层面就被消掉了，不是在代码里硬扛。

**代价**：不能在别人的段落中间插字。想补充，只能新起一段。

这个代价我认为值得付。至少第一版值得。

### 4.2 「正在写」和「已落定」是两种状态

- 正在输入的文字是**草稿**，还没进正文。
- 点右上角的**对勾** = 提交这一段。
- 提交之后，这段变成只读，落进正文，顺序固定下来。

这个交互不是我拍脑袋想的，是想做这个项目的人提出的，原话是"右上角不是会有一个打勾的选项吗，点一下那个就是确认了"。

它的好处是把「我写完了」这个动作显式化。半句话不会被别人误当成写错，也不会出现"他还在打字我却已经读到"的尴尬。

### 4.3 顺序 = 提交的先后

两个人同时写，谁先点对勾，谁在前。

这是最简单也最符合直觉的规则。它把并发问题降级成一个「到达顺序」问题——服务端按收到的顺序追加就行。

**遗留问题**：两个提交几乎同时到达怎么办？第一版用服务端收到的时间戳排序，同毫秒时用设备 ID 兜底。这条以后可能要改，先记在 §9。

### 4.4 一台机器当主机，其他人连它

写代码之前必须先回答一个问题：**谁负责保存数据？**

- **方案 A（去中心化）**：每台设备各存一份，靠同步协议合并。
  好处是没有单点。坏处是要自己设计一套一致性协议，第一阶段根本做不完。
- **方案 B（主机模式）**：一台设备"开房间"，它就是主机，数据在它那儿；其他人连过去。

**选 B。**

理由很直白：我要在两个月内看到东西能跑。B 方案里，"服务器"和"客户端"可以是同一份代码的两个角色，学习成本低，调试也直观。

**代价**：主机退出，房间就没了。所以第一版明确要求「主机别关软件」。这条以后必须解决，但不在第一版。

### 4.5 实时

局域网内走 WebSocket，延迟应该在个位数毫秒。不做跨网，不做中继，不做穿透。

局域网快是这个项目成立的前提——正因为快，"实时"才有意义。

## 5. 功能范围

### 第一版（M0 / M1）必须有

**单机部分**
- 新建、重命名、删除便签
- 便签内分段书写：写一段 → 点对勾 → 落定
- 段落顺序稳定，可上下滚动
- 数据存本地，关掉软件再开还在

**局域网部分**
- 一台机器开房间（显示本机 IP / 二维码）
- 其他机器加入（输 IP 或扫码）
- 加入后能看到房间里已有的人
- 任何人提交段落，其他人几百毫秒内看到

### 中期（M2）

- 首页显示「哪些便签正在被编辑、谁在编辑」
- 点进去可以申请加入，由主控确认一下再放进来
- 断线重连：WiFi 抖一下不至于要重开软件

### 远期（M3+，暂不定）

- 多端（macOS / Linux / 手机）
- 图片、Markdown
- 历史版本与回滚

远期的具体形状现在写就是编，等 M2 跑顺了再补。

## 6. 明确不做（第一版）

这一节是防止自己中途跑偏用的，写下来等于给自己上锁：

- **不做账号体系**。局域网内用昵称，软件关了就没了。没有密码，没有找回。
- **不做云同步**。数据不出局域网。这是特性，不是功能缺失。
- **不做富文本**。第一版只有纯文本，字体颜色字号一概没有。
- **不做字符级合并**。见 §4.1，这是设计选择不是偷懒。
- **不做端到端加密**。局域网内，第一版先不做，以后再说。
- **不做移动端**。

## 7. 技术约束

### 语言和框架

- **桌面端**：Python 3 + PySide6（Qt）
- **局域网通信**：WebSocket（`websockets` 库）
- **存储**：SQLite（Python 自带 `sqlite3`，不引入 ORM）
- **打包**：PyInstaller
- **版本管理**：Git + GitHub

选 Python 的理由很朴素：上手快、库全、我以后做数据处理也用得上，不想为了这个项目专门再学一门。

**关于"能不能 Python + Java 一起用"**：技术上可以（Python 做后端、Java 做界面），但中间要多写一层进程通信，调试复杂度翻倍，对一个人做的小项目不划算。所以选一个，选 Python。

**这个选择不是终身的。** 如果之后发现 Qt 做不出想要的界面，或者多端需求变了，可以换。所以第一版的代码量要控制在「能重写」的范围内——这也是为什么 M0 只做单机。

### 已知的代价

诚实列一下，免得以后觉得被骗了：

- PyInstaller 打出来的 exe 体积大（50MB 起步）
- 启动比原生程序慢半拍
- Qt 的默认控件长得像 2010 年的软件，界面要自己调

## 9. 还没想清楚的问题

列在这儿，不装懂：

1. 别人能看到我正在输入的内容吗？灰字预览？还是只显示"某某正在输入"？
2. 段落提交后能不能编辑或删除？还是只能追加？
3. 主机退出时，房间里的数据怎么办？（导出成文件？自动选新主机？）
4. 局域网里怎么发现彼此？IP 段扫描 / mDNS 广播 / 手动输 IP，哪个最省事？
5. 一张便签最多几个人？技术上不限制，但产品上要不要限制？
6. 要不要支持离线写、重连后补交？
7. 界面到底长什么样？便签墙？列表？还是贴在桌面上的便利贴？

第 7 条其实挺关键，但我觉得应该等 M0 能跑了再定，现在画界面是纸上谈兵。

## 10. 顺带一提：软件著作权

这个项目打算申请软件著作权，所以有两件事从现在就要注意：

1. **代码结构保持清晰**，模块边界明确（界面 / 同步 / 存储三块分开写）。这样以后写《软件说明书》省事。
2. **文档留好**。软著要提交源代码前后各 30 页和一份说明书，过程文档不提交但要能自证。

这一节不影响技术决策，只是提醒自己别把代码写成一坨。
